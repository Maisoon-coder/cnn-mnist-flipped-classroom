## 一、必答六问

### Q1 为什么要 `optimizer.zero_grad()`？

**结论**：因为 PyTorch 的梯度是**累加**的，不清零会把这批和上批的梯度加起来。

**依据**：`.backward()` 执行的是 `p.grad += ...`，不是 `p.grad = ...`。忘了清零，参数更新方向就错了，loss 会震荡甚至不收敛——这是训练不收敛的第一号原因。

**一句话**：不清零 = 把昨天的错误累积到今天。

---

### Q2 `loss.backward()` 和 `optimizer.step()` 有什么区别？

**结论**：前者**只算梯度**，后者**按梯度改参数**，是两步不是一步。

**依据**：`backward()` 沿计算图反向传播，把梯度写进 `p.grad`；`step()` 才按 `w ← w − lr × grad` 更新权重。只调 `backward()` 不调 `step()`，参数不会变。

**加分**：所以我们代码里是 `zero_grad → forward → loss → backward → step` 五步，最后一步才真正改权重。

---

### Q3 为什么用交叉熵，不用 MSE？

**结论**：分类任务上交叉熵**梯度更有效、收敛更快**；而且我们的模型直接输出 logits，交叉熵内部已含 `log_softmax`。

**依据**：MSE 配 sigmoid/softmax 时，对"已经错得很离谱"的样本梯度反而变小，学不动；交叉熵配 softmax 的梯度形式是 `p − y`，错得越狠梯度越大。

**容易踩**：模型输出**不要再套一次 Softmax**，否则等于算两遍，loss 会偏小、准确率上不去。

---

### Q4 `model.eval()` 和 `torch.no_grad()` 是一回事吗？

**结论**：不是。**前者改层的行为，后者关梯度记录**，评估时两个一起用。

**依据**：
- `eval()` 影响 Dropout（关闭）和 BatchNorm（用移动统计量）——我们这个网络没有这两种层，但习惯要立住，换网络时不至于出错；
- `no_grad()` 不构建计算图，省显存、更快。

**加分**：漏掉 `eval()` 在小网络上可能看不出来，但一旦加上 Dropout 就会出现"同一张图两次预测不一样"。

---

### Q5 怎么保证结果可复现？

**结论**：三个随机源都设种子 + 数据打乱用**独立生成器** + 记录环境版本 + 结果跨环境验证过。

**依据**：
- `random` / `numpy` / `torch` 三个种子都设为 42；
- 训练集打乱用独立的 `torch.Generator`，不复用全局状态——因为两个模型参数量不同、初始化消耗的随机数个数不同，共用全局种子会让两个模型看到**不同的样本顺序**，对比就不公平了；
- `environment.txt` 记录 Python / torch / torchvision 版本与设备。

**硬证据**：同一份权重在三个不同环境复现出一致结果——Python 3.12 + torch 2.11（组员 3）、Python 3.13 + torch 2.15（组员 5）、Python 3.14 + torch 2.15（我），四项指标逐位相同。

---

### Q6 保存权重和重新训练有什么区别？

**结论**：权重只存**参数数值**，不存优化器和训练历史；所以必须配 `config.json` 和 `seed/epoch` 才能追溯。

**依据**：我们的 `.pt` 存成字典：

```python
{"format_version": 1, "model": "cnn", "seed": 42, "epoch": 5,
 "model_state": {...}, "extra": {"run_id": ..., "n_params": 61706}}
```

这样加载时不需要再猜是哪个模型、第几轮、什么配置——验收项"权重能否追溯到配置和轮次"就是查这个。

## 三、三条兜底原则

1. **没做过就说没做。** 比如"跑过三种子吗"——答"没有，只跑了 seed=42，这是我们的已知限制"。
2. **数字不确定就报"以 README 为准"。** 全场唯一数据源是仓库 `README.md`，别凭记忆报数。
3. **解释不了的现象别硬解释。** 说"这是观察到的现象，具体原因我们没有验证"比编一个理由安全得多。
